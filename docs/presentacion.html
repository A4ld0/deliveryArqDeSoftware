Angular 20 Node.js + Express PostgreSQL Supabase Auth SSE Tiempo Real Leaflet Maps
¿Qué es?

Una plataforma completa
de delivery multi-rol

Conecta clientes, restaurantes y repartidores en tiempo real.

🎯
Objetivo
Demostrar los principios de Arquitectura de Software aplicados: separación de capas, patrones de diseño, comunicación en tiempo real y seguridad basada en roles.
📐
Arquitectura
Monorepo con dos aplicaciones independientes: un API REST en Express/TypeScript y un SPA en Angular 20 con componentes standalone y signals.
👥
Cuatro roles independientes
Cada rol tiene sus propias rutas, guards, vistas y permisos. Un mismo usuario solo puede tener un rol asignado.
⚡
Tiempo real sin WebSockets
Seguimiento GPS del repartidor y cambios de estado del pedido usando Server-Sent Events (SSE), ligero y sin overhead de WS.

State Machine

Flujo de estados de un pedido

State machine controlada en el backend — cada transición valida rol y estado actual.

🕐 PENDING cliente
→
✅ ACCEPTED restaurante
→
🍽️ READY restaurante
→
🛵 ASSIGNED repartidor
→
📍 IN_TRANSIT repartidor
→
🎉 DELIVERED repartidor
REJECTED
← desde PENDING (restaurante)
CANCELLED
← PENDING o ACCEPTED (cliente)

Cada cambio de estado publica un evento SSE → el cliente recibe la actualización en tiempo real sin polling. Al cancelar, el pago pasa automáticamente a SIMULATED_REFUNDED.

Tiempo Real

Server-Sent Events

Una sola conexión HTTP unidireccional — sin overhead de WebSockets.

📡
GET /events/orders/:id
Stream SSE de cambios de estado. El cliente se suscribe al crear un pedido y recibe eventos cuando el restaurante o repartidor actualizan el estado.
📍
GET /events/orders/:id/location
Stream SSE de coordenadas GPS. El repartidor publica su ubicación cada segundo — el mapa del cliente actualiza el pin en tiempo real.
event: order_status_changed
data: {"status":"ACCEPTED","orderId":42}

event: location_update
data: {"lat":20.659,"lng":-103.349}

event: order_status_changed
data: {"status":"DELIVERED","orderId":42}
SSE Broker almacena suscripciones en memoria
Reconexión automática del browser (EventSource API)
JWT del cliente valida acceso al stream

🔄
Trigger: updated_at
Actualización automática del timestamp en todas las tablas mediante función `set_updated_at()` en PostgreSQL.
🔐
Auth sin RLS
Supabase solo gestiona identidad (JWT). El control de acceso se implementa en el API con middlewares de rol — sin Row Level Security para mayor control explícito.
💾
Backup completo
DB_Backup/ incluye schema completo, 5 migraciones numeradas y seed con 6 restaurantes de prueba.
Funcionalidades

Características destacadas

Implementaciones no triviales del proyecto.

🗺️
Mapa en tiempo real
Leaflet.js con SSE — el pin del repartidor se mueve en el mapa del cliente sin ningún polling.
📍
Geocodificación bidireccional
Nominatim: dirección → coordenadas al buscar, y coordenadas → dirección al mover el pin en el mapa.
🔒
Auth sin SDK de Supabase en el API
El backend verifica JWTs directamente vía JWKS — sin dependencia del SDK de Supabase, más portable y controlado.
⚙️
State machine de pedidos
Transiciones validadas en `domain/order-status.ts` — cada rol solo puede ejecutar las transiciones que le corresponden.
🛒
Carrito persistente
El carrito se guarda en localStorage y se restaura al recargar la página — resistente a refreshes accidentales.
💳
Pagos + reembolsos simulados
Flujo completo: pago en la creación, reembolso automático al cancelar (SIMULATED_REFUNDED), todo en la misma transacción de BD.
SRS — Requisitos Funcionales

Requisitos funcionales clave

Selección del SRS · Equipo 4 · 22 requisitos funcionales documentados

REQ-SRS-01
Menús dinámicos — el restaurante actualiza platillos; los clientes ven disponibilidad al instante sin recargar.
REQ-SRS-02
Seguimiento en tiempo real — cambios de estado del pedido y ubicación GPS del repartidor vía SSE.
REQ-SRS-03
Geolocalización — el cliente selecciona dirección de entrega en mapa; el sistema geocodifica con Nominatim.
REQ-SRS-04
Actualizaciones del repartidor — el driver transmite coordenadas GPS en tiempo real durante cada entrega activa.
REQ-SRS-08
RBAC — control de acceso basado en roles; cliente, restaurante, repartidor y admin acceden solo a sus funciones.
REQ-SRS-14
Carrito persistente — el carrito se guarda en localStorage entre sesiones, resistente a recargas accidentales.
REQ-SRS-20
Cancelación de pedidos — el cliente puede cancelar en PENDING o ACCEPTED; el sistema genera reembolso automático.
REQ-SRS-22
Historial de pagos — registro completo con estado (aprobado / reembolsado) asociado a cada pedido.

SRS — Riesgos

Gestión de riesgos

Matriz de riesgos identificados en el SRS · R01–R07

ID Riesgo Prob. Impacto Mitigación
R01 Pérdida de conexión SSE Media Alto Reconexión automática via EventSource; fallback a polling
R02 Sobrecarga del servidor de BD Baja Alto Pool de conexiones pg, índices en columnas de búsqueda frecuente
R03 Token JWT expirado / inválido Media Medio Interceptor Angular renueva sesión antes de expirar; 401 redirige a login
R04 GPS del repartidor impreciso Media Bajo Se almacena y muestra el campo accuracy; umbral de precisión en UI
R05 Falla en geocodificación Nominatim Baja Medio Input manual de dirección como fallback; validación mínima de longitud
R06 Cambio de estado concurrente Baja Alto Transacciones de BD + state machine validan transición antes de escribir
R07 Límite de presupuesto Azure ($100) Media Medio Supabase free tier para BD; Azure reservado para despliegue final
